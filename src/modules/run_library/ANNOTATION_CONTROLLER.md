# B-RUN-02 — Snapshot-bound annotation management (offline candidate)

Status: implemented; portable automated tests PASS. Actual Windows/SQLite controller binding and native UI NOT_RUN. No evidence or database schema modification.

## Boundary

public/annotation_controller.hpp exposes AnnotationController::rename(Row, name) and set_favorite(Row, bool) over the existing injected QueryRepository. It reuses presentation::History::find, Record, Annotation, ReadState and validation from B-RUN-01 and the existing repository. A Row is a caller-owned copied selection snapshot: exact full indexed record (stable run ID, manifest SHA-256, category/profile/semantics, origin/status and nullable timing) and separately observed annotation plus its read state. No list-index identity, path input, new database, native engine dependency, or direct archive access. Controller borrows a repository which must outlive it; no owned persisted state, queue, thread, or automatic retries. Optional feature: do not construct or expose commands if management disabled or storage unavailable. History can continue independently on its read-only port.

Commands are explicit user intent, not toggles or implicit background mutations. UI retains the selected Row at submission, discards unsubmitted intents on selection change and submits copied values to the same repository owner thread used by the history/repository composition. No UI/frame-thread I/O. All operations, including reads and other writers, must be serialized by the composition root on that owner thread; do not share the borrowed repository between concurrent controllers. NativeRepository currently uses BEGIN IMMEDIATE and INSERT OR REPLACE only in the labels table, with foreign-key constraint and existing name validation; no controller changes to it. This preflight/readback is optimistic value checking under the single-owner contract, NOT a database compare-and-swap or cross-process transaction. No detection of ABA (a value changed then restored) or currently selected UI row beyond the submitted snapshot, no protection from concurrent external writers, compromised adapters, or tampering. An atomic annotation CAS would require an explicitly reviewed repository port/adapter change; not introduced here.

## Behavior

Validate selection record and annotation before I/O; reject unknown/invalid annotation read state rather than treat it as absence. Rename accepts valid UTF-8 1..256 bytes, existing C0/C1 control rejection, exact bytes, no truncation, normalization or interpretation as a path. Preserve selected favorite bit. Set favorite takes desired bool and preserves selected name. For a previously absent annotation, favorite=true uses the stable run ID as deterministic neutral display name (existing schema requires nonempty name); false is a no-op with no row creation. Rename absent annotation creates explicit name and favorite=false. Removing favorite keeps existing label; no label deletion. All stored origin classifications may be annotated without upgrading provenance or granting any PB/eligibility.

Read fresh Detail via existing History, compare entire validated Record with immutable selected snapshot using identical(), including digest even when run ID matches; refuse mismatch, absent/malformed data or unavailable storage. Compare exact whole optional annotation (both fields and presence). If current equals desired, return unchanged with observed row and no write, even on explicit retry after lost acknowledgement. Otherwise require current equals selected annotation; stale values are not merged or silently overwritten, including a rename whose favorite changed or a favorite whose name changed. Caller refreshes and explicitly resubmits if appropriate. If eligible, call existing annotate exactly once. Then read fresh Detail exactly once and require entire record still identical and annotation exactly desired before reporting updated. Never invoke insert, recent, best_local, archive, staging or delete operations. Per command at most two record reads, two annotation reads, one annotation write; inputs use existing bounds. No scans or persistent command history.

## Results and UI handling

EditResult separates EditStatus, WriteState (not_attempted/returned/threw) and optional validated observed Detail (preflight or post-attempt). For invalid input/selection no I/O and no observation. Missing/unavailable/invalid data, evidence_conflict, stale_annotation stop without writes and return available observation. Preflight mismatched returned ID or malformed values are invalid_data; native repository exceptions are unavailable per History contract. Invalid selected annotation is selection_unavailable, structurally inconsistent selection invalid_request. unchanged and updated carry exact observed record/annotation. If annotate throws, return write_uncertain even if post-attempt read shows desired value; caller may refresh, and a later explicit identical command is a no-op if already applied. If write returns but observed record/annotation missing, unreadable, corrupt, mismatched or changed, return readback_uncertain. Both uncertain statuses preserve observed Detail and distinguish a possibly committed write from a preflight failure; never report success, automatically retry, repair or roll back by overwriting another edit. A broken adapter could have mutated evidence despite the contract; readback can detect visible inconsistency but cannot prevent or repair it. Do not infer durable commit, actual evidence verification or power-loss recovery from a readback match. Generic operation errors are exposed as typed status rather than propagating raw storage exception messages containing private paths.

No deletion, retention, import/export side effects, playback, native hooks, local admission, archive index promotion, or official PB. Actual ArchiveSource binding from B-RUN-01 requires coordination on existing verifier/controller payload; not changed here. Shared contracts, NativeRepository, existing storage tools and schema untouched. No new dependencies.
